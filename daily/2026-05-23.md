## 一、Handbook 四大模块逻辑关系

> **核心洞察**：AI 提供理解/生成层（理解世界 → 生成行动），Web3 提供信任/执行层（确定性规则 → 不可篡改记录），Bridge 是它们交汇的地带，前沿探索是把这套体系产品化。

### 模块关系图

```
┌─────────────┐     ┌─────────────┐
│  Module 1   │     │  Module 2   │
│  AI 基础    │     │  Web3 基础  │
│             │     │             │
│ 理解 + 生成  │────▶│ 信任 + 执行  │
│ 概率性      │     │ 确定性      │
│             │     │             │
└──────┬──────┘     └──────┬──────┘
       │                   │
       │    ┌──────────┐   │
       └───▶│ Module 3 │◀──┘
            │  Bridge  │
            │  交叉层   │
            │          │
            │ AI 的生成│
            │ + Web3   │
            │ 的可验证 │
            │ 执行     │
            └────┬─────┘
                 │
                 ▼
            ┌──────────┐
            │ Module 4 │
            │ 前沿探索  │
            │          │
            │ 产品化    │
            │ Hackathon│
            └──────────┘
```

### 为何这个顺序？

| 阶段 | 模块 | 解决什么问题 | 为什么先学它 |
|------|------|-------------|-------------|
| 1 | **AI 基础** | 模型怎么"想"、怎么说、怎么做 | 没有理解 AI 的能力边界，就没法设计 Agent |
| 2 | **Web3 基础** | 链上怎么"存证"、怎么"执行" | 没有理解链上确定性，Agent 的交易就是盲操作 |
| 3 | **Bridge 交叉** | AI 和链如何安全协作 | 把两个领域的能力拼在一起，产生 1+1>2 |
| 4 | **前沿探索** | 能做出什么产品/原型 | 用前三层的知识构建可交付的东西 |

### 概念如何在模块间流动

```
Module 1: LLM 概率生成
    ↓ "模型说什么不一定对"
Module 2: 智能合约确定执行
    ↓ "链上执行什么就一定是什么"
Module 3: Verifiable AI / Chain-aware Context
    ↓ "让 AI 的生成在链上可验证/可追溯"
Module 4: Agentic Commerce / Wallet Permission
    ↓ "把可验证的 AI Agent 变成产品"
```

### Stan 的已有工作如何嵌入这个框架

| Stan 的项目 | 对应层 | 说明 |
|------------|--------|------|
| **交易解释器** | 认知层 | AI 读取链上数据 → 生成人类可读的风险摘要 |
| **风险提示 Prompt** | 保护层 | Prompt 作为软约束，在"认知"和"行动"之间插入一层检查 |
| **Context 分层设计** | Bridge 前奏 | 指令层/任务层/事实层/知识层/记忆层 — 已是 Chain-aware Context 的原型 |

> 关键认知：**Prompt 是软约束，不是安全边界**。真正的安全在链上的确定性执行（Module 2）和 Bridge 层的可验证设计（Module 3）。AI 做的事是"理解 + 建议"，Web3 做的事是"验证 + 执行"。

## 二、Module 1 逐章连接分析 + 小练习

### 1.1 → 1.2：LLM → Prompt
**从概率生成到可控输出**

LLM 的本质是 next token prediction —— 给定上文，猜下一个最可能的 token。Prompt 工程的本质是：**通过精心设计的输入，把概率空间约束到你想要的区域**。

| 维度 | LLM（无 Prompt 工程） | Prompt 工程后 |
|------|----------------------|--------------|
| 输出 | 不可预测的概率采样 | 结构化、可检查的 JSON |
| 安全 | 无法保证 | 软约束（但不等于安全边界） |
| 可靠性 | 依赖运气 | 依赖设计 + 验证 |

**🛠️ 练习 (10 min)**：设计对比实验
```python
# 同一个任务，三种 prompt 质量，观察输出差异
task = "分析这笔交易的风险：0x795c3d4d..."

# Level 1: 无结构
prompt_v1 = f"分析风险: {task}"

# Level 2: 有结构但无约束
prompt_v2 = f"""分析以下交易风险:
交易: {task}
请从资金安全、合约风险、授权风险三个维度分析"""

# Level 3: 结构化 + 输出格式约束
prompt_v3 = f"""你是一个 Web3 安全分析器。
交易: {task}
按以下 JSON 输出:
{{"risk_level": "low|medium|high|critical",
  "risks": [{{"category": "", "description": "", "severity": ""}}],
  "recommendation": ""}}"""

# 跑三次对比，观察结构化如何影响输出质量
```

### 1.2 → 1.3：Prompt → Context
**上下文如何扩展 prompt 的边界**

Prompt 是一段指令，Context 是 Prompt 周围的所有信息环境。Prompt 告诉模型"做什么"，Context 描述"在什么情况下做"。

> 关键认知：**Context window 有限（DeepSeek V4 1M tokens ~= 一本《三体》）**。Context 管理的本质是：在有限窗口内，放入最有价值的信息。

| 概念 | 说明 |
|------|------|
| Prompt | "请分析这笔交易" |
| Context | 交易详情 + 链上状态 + 用户偏好 + 历史记录 + 安全规则 |
| Context Window | 1M tokens 上限，决定了能"记住"多少 |
| Context 分层 | 指令层 > 任务层 > 事实层 > 知识层 > 记忆层（按重要性排序） |

**🛠️ 练习 (10 min)**：Context 分层填充表
```
场景：交易解释器 Agent 分析一笔 swap 交易

指令层（不可变系统规则）：
  - 你是交易安全分析器，输出 JSON 格式
  - 不确定时标记 risk_level=unknown，不允许猜测
  - 禁止执行任何链上交易

任务层（本次会话参数）：
  - 用户: 0xAlice, 目标: 分析 tx 0x795c...
  - 用户关注: 资金安全 > gas > 速度

事实层（链上实时数据）：
  - tx 详情: {from, to, value, data, logs}
  - 当前 gas: 25 gwei, ETH: $3200
  - 合约 0xTarget 审计状态: 未审计

知识层（参考文档）：
  - ERC-20 approve 风险模式
  - 常见 phishing 合约特征

记忆层（用户历史）：
  - Alice 上次拒绝了类似的高风险 tx
  - Alice 偏好: 任何 >$1000 的交易需要额外确认

问题: 如果 Context Window 只有 4000 tokens，你删哪些？为什么？
```

### 1.3 → 1.4：Context → RAG
**从静态上下文到动态检索**

Context 的问题：信息是提前准备好的，受窗口大小限制。RAG（Retrieval-Augmented Generation）解决的是：**需要时动态检索相关知识，只把最相关的放入 Context**。

| 维度 | 纯 Context | Context + RAG |
|------|-----------|---------------|
| 知识容量 | 受窗口限制（1M tokens） | 理论上无限（向量数据库） |
| 时效性 | 静态，需手动更新 | 动态，实时检索最新文档 |
| 精准度 | 全量载入，注意力稀释 | 只载入相关片段，聚焦 |
| 复杂度 | 低 | 需要 embedding + 检索 + 排序 |

**🛠️ 练习 (15 min)**：RAG 对比思考实验
```
场景：交易解释器需要判断一个合约地址是否安全

方案 A（纯 Context）:
  把所有已知恶意地址列表塞入 Context → 窗口炸了

方案 B（RAG）:
  1. 把已知恶意地址做 embedding → 向量库
  2. 收到新地址时做相似度检索
  3. 只把 Top-5 最相似结果放入 Context
  4. Prompt: "该地址与以下 5 个已知恶意地址相似度: ... 判断风险"

对比输出一个表格:
| 维度 | 方案 A | 方案 B |
| 准确性 | 全量但注意力稀释 | 聚焦但可能漏检 |
| 效率 | 窗口压力大 | 检索 + 推理分离 |
| 维护 | 需全量替换 | 增量更新向量库 |
```

### 1.4 → 1.5：RAG → Agent
**从单一推理到工具调用 + 多步执行**

RAG 是"查资料 → 回答"。Agent 是"查资料 → 思考 → 调用工具 → 观察结果 → 再思考 → 再行动 → ... → 回答"。Agent = RAG + 工具调用 + 循环决策。

| 能力 | RAG 系统 | Agent 系统 |
|------|---------|-----------|
| 检索知识 | ✅ | ✅ |
| 调用 API | ❌ | ✅ |
| 多步推理 | ❌ | ✅ (ReAct / Plan-Execute) |
| 环境交互 | ❌ | ✅ (读写链上状态) |
| 错误恢复 | ❌ | ✅ (观察失败 → 换策略) |

**🛠️ 练习 (15 min)**：ReAct 循环纸笔推演
```
任务: Agent 帮用户分析一笔 swap 交易是否安全

ReAct 循环:

Step 1 — Thought: 我需要交易详情
         Action: call etherscan_api(tx_hash)
         Observation: {from: 0xAlice, to: 0xUnverifiedContract, value: 5 ETH, data: 0xSwapFunc...}

Step 2 — Thought: 目标合约未验证，需要检查代码
         Action: call blockscout_source_code(0xUnverifiedContract)
         Observation: 合约未开源，无法获取源码

Step 3 — Thought: 未开源是高风险信号。还需要查历史
         Action: call risk_database(0xUnverifiedContract)
         Observation: 3 条投诉，标记为"疑似钓鱼"

Step 4 — Thought: 证据足够，判断为高风险
         Action: return_result({risk: "critical", reason: "unverified + phishing reports"})

问题: 如果 Step 2 中 blockscout 返回了源码，Agent 下一步应该做什么？
```

### 1.5 → 1.6/1.8：Agent → Frameworks & MCP
**协议和框架如何标准化 Agent 开发**

自己做 Agent：手写 ReAct 循环 + 手写工具函数 + 手写 prompt 管理。用框架：LangChain/LlamaIndex/CrewAI 提供标准化的 pipeline。MCP（Model Context Protocol）标准化的是：**工具如何被注册、发现和调用**。

| 层 | 自己实现 | 框架/MCP 提供 |
|-----|---------|--------------|
| 推理循环 | 手写 while + Thought/Action/Observation | AgentExecutor / CrewAI Task |
| 工具管理 | 手写 if-else dispatch | MCP Server 注册 + Tool schema |
| 记忆管理 | 手写 append 到 context | LangChain Memory / 向量存储 |
| 工具发现 | 硬编码工具列表 | MCP list_tools() 动态发现 |

> 关键认知：MCP 之于 Agent，就像 USB-C 之于外设。它不解决"Agent 应该做什么"，而是解决"Agent 如何安全地发现和调用工具"。

**🛠️ 练习 (10 min)**：MCP 工具注册对比
```python
# 方案 A：手写工具调度（你现在的做法）
def call_tool(tool_name: str, params: dict):
    if tool_name == "etherscan":
        return query_etherscan(params["tx_hash"])
    elif tool_name == "risk_check":
        return check_risk(params["address"])
    # ... 每加一个工具改一次 dispatch

# 方案 B：MCP 风格的工具注册
class ToolRegistry:
    def __init__(self):
        self.tools = {}

    def register(self, tool):
        self.tools[tool.name] = tool  # tool 自带 schema + handler

    def list_tools(self):
        return [{"name": t.name, "schema": t.schema} for t in self.tools.values()]

    def call(self, name, params):
        return self.tools[name].run(params)

# 对比：方案 B 加新工具不需要改 dispatch 代码
# 思考：你的交易解释器如果改造成 MCP 风格，需要改哪些部分？
```

### 🧩 Module 1 连接全景总结

```
LLM（概率生成）
  │  约束手段: Prompt Engineering
  ▼
Prompt（结构化输入，软约束）
  │  扩展手段: Context 分层
  ▼
Context（信息环境管理）
  │  扩容手段: RAG 动态检索
  ▼
RAG（按需检索知识）
  │  升级手段: 工具调用 + 循环决策
  ▼
Agent（多步推理 + 行动）
  │  标准化手段: Frameworks + MCP
  ▼
Frameworks / MCP（生产级 Agent 基础设施）
```

每一步都在解决上一步的瓶颈：
- Prompt 解决 LLM 的"不可控"
- Context 解决 Prompt 的"信息不足"
- RAG 解决 Context 的"窗口有限"
- Agent 解决 RAG 的"只能读不能做"
- MCP 解决 Agent 的"工具难以标准化"

   - Context → 分层管理信息来源
   - 下一步自然延伸：RAG（动态安全知识库）→ Agent（自动决策）→ MCP（标准化工具）

3. **"软约束 vs 硬约束"是贯穿全线的核心概念**：
   - Prompt = 软约束（可以被绕过）
   - 智能合约 = 硬约束（代码即法律，不可绕过）
   - Bridge 层的价值 = 把 AI 的软约束连接到 Web3 的硬约束
