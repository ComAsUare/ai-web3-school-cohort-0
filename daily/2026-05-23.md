## 二、Module 1 章节连接 + 迷你练习

### 连接 1：LLM → Prompt — 从概率生成到可控输出

**核心关系**：
- LLM 本质是一个**概率分布模型**：给定前文 `x₁...xₙ`，预测下一个 token 的概率 P(token | x₁...xₙ)
- Prompt 是在这个概率空间里**划定搜索边界**：通过 System Prompt 设定角色域，通过 User Prompt 设定任务域
- 没有 Prompt 的 LLM 是「什么都能说」的万能补全器；加了 Prompt 才变成「在特定约束下推理」的问题解决器

```
LLM（裸模型）                        LLM + Prompt（受约束模型）
─────────────────                   ─────────────────────────
输入: "以太坊是"                     输入: System: 你是Web3安全专家
输出: 概率最高的续写                     User: 分析这笔交易的风险
      (可能是百科/新闻/项目介绍)         输出: 结构化风险评估报告

没有「对错」只有「概率」              有「任务-输出」的约束关系
```

### 连接 2：Prompt → Context — 上下文如何扩展 Prompt 的边界

**核心关系**：
- Prompt 定义了「任务契约」（角色 + 目标 + 格式），但它本身是**静态的**
- Context 是「运行时注入的知识」——对话历史、文档片段、链上数据、用户偏好
- Prompt + Context = 模型实际看到的完整输入。**Context 的质量直接决定输出的质量**。

```
Prompt（不变）               Context（变化）              输出变化
─────────────────           ────────────────            ──────────
"你是安全分析师"     +       (空上下文)          →      泛泛的安全建议
"你是安全分析师"     +       3 笔历史交易记录      →      基于模式的判断
"你是安全分析师"     +       实时链上 calldata    →      针对当前交易的精确判断
```

**关键教训**：你的交易解释器之所以有效，不是因为 Prompt 写得好，而是因为 **Context 里放了真实的 calldata JSON**。这就是 Context 的力量——它把 AI 从「凭记忆猜测」变成「基于证据推理」。

### 连接 3：Context → RAG — 从静态上下文到动态检索

**核心关系**：
- Context 是「你塞给模型的知识」，RAG 是「模型自己去找的知识」
- 传统 Context：开发者手动拼接（适合固定知识，如 System Prompt、已确认的数据）
- RAG：运行时检索 → 动态注入（适合变化的知识，如最新文档、实时数据、私有知识库）

```
静态 Context 模式                    动态 RAG 模式
─────────────────                   ─────────────────
用户问 → 固定 Prompt+Context        用户问 → Embedding 检索
          ↓                                  ↓
       模型回答                        找到相关文档片段
                                           ↓
                                      注入为 Context
                                           ↓
                                        模型回答

适合: 角色设定、输出格式          适合: FAQ、文档问答、链上数据查询
```

**为什么这个连接重要**：你的交易解释器目前是「静态 Context」模式（手动查询 API → 塞给 LLM）。升级到 RAG 意味着：Agent 自己决定「需要查什么」，然后自动检索、注入、推理。

# === 模式 A：静态 Context（你当前的做法）===
def static_context_answer(question):
    # 把所有知识都塞进去（不现实，知识库大了就塞不下）
    all_context = "\n".join([kb["text"] for kb in knowledge_base])
    prompt = f"知识库:\n{all_context}\n\n问题: {question}\n回答:"
    # → 调用 LLM
    return prompt  # 你会看到 context 越来越长，超出 token 限制

# === 模式 B：RAG 风格（简单关键字匹配模拟检索）===
def rag_style_answer(question):
    # Step 1: 检索（这里用关键字匹配模拟 embedding 检索）
    keywords = question.lower().split()
    relevant = []
    for kb in knowledge_base:
        if any(kw in kb["text"].lower() for kw in keywords):
            relevant.append(kb)

    # Step 2: 只注入相关文档
    context = "\n".join([r["text"] for r in relevant])

    # Step 3: 如果没有相关文档，诚实告知
    if not relevant:
        return "未找到相关安全知识，建议谨慎处理。"

    prompt = f"相关知识:\n{context}\n\n问题: {question}\n回答:"
    return prompt

    print()

### 连接 4：RAG → Agent — 从单一推理到工具调用+多步执行

**核心关系**：
- RAG 解决了「知识从哪里来」，但它仍然是**单步推理**：检索 → 注入 → 回答
- Agent 在此基础上加了**行动循环**：推理 → 决定调用工具 → 获取结果 → 再推理 → 再决定 → ... → 最终回答
- 核心差异：RAG 只能「查资料然后回答」，Agent 能「查资料 → 发现问题 → 调用更多工具 → 执行动作」

```
RAG 模式                          Agent 模式
───────────                       ───────────
用户: 分析这笔交易                    用户: 分析这笔交易，风险高就阻止
  ↓                                    ↓
检索 calldata 文档                  Thought: 需要查 calldata
  ↓                                    ↓
注入 Context + 回答                Action: 调用 blockscout API
                                     ↓
                                  Observation: 拿到 calldata
                                     ↓
                                  Thought: 是 transferFrom + 未知地址
                                     ↓
                                  Action: 查该地址是否已验证合约
                                     ↓
                                  Observation: 未验证，高风险
                                     ↓
                                  Thought: 应阻止 + 警告用户
                                     ↓
                                  Final: 输出阻止建议 + 安全解释
```

        "0xBBB": {"to": "0xUniswapRouter", "selector": "swapExactETHForTokens", "value": "0.5 ETH"},
    }
    return mock_data.get(tx_hash, {"error": "not found"})

def is_verified_contract(address):
    """模拟：检查合约是否已验证"""
    verified = ["0xUniswapRouter", "0xAavePool"]
    return address in verified

# --- Agent 的 ReAct 循环 ---
def agent_analyze(user_input):
    """极简 ReAct Agent：推理(Thought) → 行动(Action) → 观察(Observation) → 循环"""

    # 这里用硬编码的规则模拟 Agent 的推理（真正的 Agent 用 LLM 做决策）
    # 但结构是真实的 ReAct 模式

    steps = []
    tx_hash = user_input.get("tx_hash", "0xBBB")

    # Step 1: 获取 calldata
    steps.append({"thought": "需要先查询交易 calldata", "action": f"get_calldata({tx_hash})"})
    calldata = get_calldata(tx_hash)
    steps.append({"observation": calldata})

    # Step 2: 检查 selector
    selector = calldata.get("selector", "")
    if "transferFrom" in selector:
        steps.append({"thought": "检测到 transferFrom，需要验证接收方地址"})
        to_addr = calldata.get("to", "")
        verified = is_verified_contract(to_addr)
        steps.append({"action": f"is_verified_contract({to_addr})"})
        steps.append({"observation": verified})

        if not verified:
            steps.append({"thought": "接收方未验证 + transferFrom → 高风险！"})
            return {
                "risk": "HIGH",
                "action": "BLOCK",
                "reason": "transferFrom to unverified contract",
                "steps": steps,
            }

    # Step 3: 检查 swap 场景
    if "swap" in selector.lower():
        to_addr = calldata.get("to", "")
        verified = is_verified_contract(to_addr)
        steps.append({"thought": f"检测到 swap 操作，验证目标合约 {to_addr}"})
        steps.append({"observation": verified})
        if verified:
            steps.append({"thought": "已在 DEX 白名单，低风险"})
            return {"risk": "LOW", "action": "ALLOW", "reason": "swap on verified DEX", "steps": steps}

    return {"risk": "MEDIUM", "action": "WARN", "reason": "需要更多信息", "steps": steps}

### 连接 5：Agent → MCP / Frameworks — 协议和框架如何标准化 Agent 开发

**核心关系**：
- 手写 Agent 的痛点：工具调用格式不统一，每次换模型都要改代码，多 Agent 协作靠 ad-hoc
- **Frameworks**（LangChain、CrewAI、OpenAI Agents SDK）解决了「开发效率」问题——提供标准化的工具定义、memory、编排模式
- **MCP**（Model Context Protocol）解决了「互操作」问题——让任何 Agent 都能用同一套协议发现和调用工具/资源

```
手写 Agent                          Framework + MCP
──────────                          ────────────────
                                     ┌─────────────┐
工具: 自己写 adaptor                │   你的 Agent │
       │                             │  (业务逻辑)   │
模型: 硬编码 API 调用                └──┬───┬───┬──┘
       │                               │   │   │
编排: if-else / 手写循环              MCP │   │   │ Framework
       │                            ┌──┴─┐ │   │  ┌──────────┐
痛点: 每个工具一种调法               │工具A│ │   └──┤ LangChain │
      每个模型一种接口               └────┘ │      │ CrewAI    │
      改一处全部重写                   ┌───┴─┐    └──────────┘
                                      │工具B │
                                      └─────┘
                                  MCP 统一了工具发现/调用协议
                                  Framework 统一了 Agent 编排模式
```

**Stan 的实际情况**：你目前用的是手写模式 — Skill 触发 + ad hoc 工具调用。这在小规模（1-2 个工具）时最灵活。当工具数量 >5 或需要多 Agent 协作时，就该考虑 Framework + MCP 了。

### 🔗 Module 1 连接总结

```
LLM ──→ Prompt ──→ Context ──→ RAG ──→ Agent ──→ MCP/Frameworks
 │         │          │          │         │            │
概率模型   约束边界    知识注入    动态检索   行动循环     标准化
 │         │          │          │         │            │
"能说话"  "好好说话"  "说对的话" "找对信息" "做对的事"  "大家都能做"
```

**每一环的跃迁**：
| 跃迁 | 解决的问题 | 新增能力 |
|------|-----------|---------|
| LLM → Prompt | 输出不可控 | 角色约束 + 格式约束 |
| Prompt → Context | 背景知识缺失 | 运行时注入外部知识 |
| Context → RAG | 知识量超过窗口 | 按需检索 + 动态注入 |
| RAG → Agent | 只能回答不能执行 | 工具调用 + 多步推理 |
| Agent → MCP | 工具/Agent 不互通 | 统一协议 + 互操作 |

### 💡 Insights & Reflections | 收获与思考

**What I Learned | 今日收获**:

1. **Handbook 的逻辑不是「百科分类」，而是「能力栈」**：
   - AI 基础 = 学会使用工具（Agent 的能力）
   - Web3 基础 = 理解舞台规则（链的约束）
   - Bridge = 工具在舞台上表演的编排艺术
   - 前沿 = 看到完整演出的场景
   - 这个视角比「先学 A 再学 B」的线性思维有价值得多

2. **Module 1 的 5 个跃迁是层层叠加的**：
   - 不是 6 个独立章节，而是一条「从会说到会做」的进化链
   - 你的交易解释器停在第 3→4 跃迁之间（有 Context + 手动检索，但缺自动工具调用）
   - 下一个突破点：把交易解释器升级为真正的 Agent（自动决定查什么、查谁、然后行动）

3. **Framework 选型的时机判断**：
   - 手写 Agent（当前）：工具 ≤3 个，逻辑清晰 → 继续手写，保持灵活
   - 引入 Framework 的信号：工具 ≥5 个，出现「我需要记哪个工具叫什么」；多 Agent 协作需求出现

**Problems Encountered | 遇到的问题**:

**Thoughts | 思考与感悟**:
