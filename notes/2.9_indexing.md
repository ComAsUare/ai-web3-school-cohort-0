## 索引要能重放：
合约升级、reorg、bug 修复时，需要从某个区块重新构建数据
## 设计 event 时要考虑后续查询：

event 是否包含关键地址；
是否需要 indexed 参数；
是否能从 event 还原业务状态；
失败交易不会产生成功 event；
合约升级后 event 是否兼容。

## solidty index:
以太坊在存储事件日志（Logs）时，把数据分成了两个区域：Topics 和 Data。

Topics（索引区）：

每一个事件最多只能有 4 个 Topic。

Topic 0：永远留给事件本身的签名哈希（例如 keccak256("Transfer(address,address,uint256)")），用来让系统知道这是什么事件。

Topic 1, 2, 3：留给被标记为 indexed 的参数。这就是为什么一个事件最多只能有 3 个参数被标记为 indexed

## subgraph
GraphQL 是由 Facebook 开发并开源的一种用于 API 的数据查询语言。它是为了解决传统 RESTful API 的痛点而生的。前端查询时提供一个querry schema.
Subgraph（子图） 特指去中心化索引协议 The Graph 中的核心概念
subgraph需要维护：需要维护：合约地址变更、事件结构变化、reorg、同步延迟和 schema 设计都会影响数据质量。
